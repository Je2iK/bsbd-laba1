Лабораторная работа №1
Проектирование базы данных (в соответствии с вариантом) и классификация данных

 

Цель: спроектировать доменную схему, классифицировать данные и настроить доступ с разделением обязанностей

 

1.  ER-модель и классификация

    ● Сформируйте ER-диаграмму домена с указанием ключей и связей.

    ● Выполните классификацию данных на уровнях (пример): Public, Internal, Confidential, Restricted (PII/персональные, фин. данные и т.п.). Сформируйте матрицу «колонка → класс».

2. DDL и схемы

    ● Создайте схемы app, ref, audit, stg. Реализуйте DDL (PK, FK, UNIQUE, CHECK, индексы (где они необходимы), NOT NULL).

    ● Сгенерируйте тестовые данные (≥ 10 строк в ключевых таблицах).

3.  Роли и привилегии

    ● Спроектируйте и создайте роли: app_reader, app_writer, app_owner, auditor; и роли разделения обязанностей: ddl_admin, dml_admin, security_admin.

    ● Назначьте привилегии на уровне схем/таблиц/последовательностей. Настройте default privileges, запретите PUBLIC доступ.

    ● audit-схема доступна на чтение только auditor; INSERT туда только через триггеры.

    ● Подготовьте сценарии проверки: какие роли что видят/могут изменять.

4. Логирование подключений пользователей

    ● Создайте таблицу audit.login_log (login_time, username, client_ip) и триггер или функцию, которая при подключении пользователя (через event trigger или SECURITY DEFINER-функцию при старте сессии) записывает информацию о входе. Протестируйте под разными ролями.

 

Обязательное в отчете: ER-диаграмма, матрица классификации, DDL со схемами и ограничениями, роли и их привилегии, тесты доступа, лог подключений


Правила оформления и сдачи отчётов
Общие требования ко всем работам:   

    ● Отчёт присылается в формате pdf.

    ● Наименование отчёта: БСБД_ФамилияИ.О._ЛРx.pdf

    ● Оформление работы - ГОСТ 7.32 - 2017

    ● Схемы - ГОСТ 19.002-80

    ● СУБД: PostgreSQL 14 и выше.

    ● Расширения: pgcrypto, pgaudit. По желанию: wal2json, pgTAP.

    ● Схемы: app (бизнес-данные), ref (справочники), audit (аудит), stg (временные/обслуживающие).

    ● Роли: app_reader, app_writer, app_owner, auditor; и роли разделения обязанностей: ddl_admin (DDL), dml_admin (массовый DML), security_admin (ключи/политики).

    ● Базовая безопасность:

            — REVOKE для PUBLIC; настройте DEFAULT PRIVILEGES.

            — Для таблиц с RLS ­– FORCE ROW LEVEL SECURITY.

            — SECURITY DEFINER-функции с безопасным search_path ('app, public').

            — Логин-роли – NOINHERIT, минимум прав.

    ● Развёртывание: SQL-скрипты и/или docker-compose; все шаги должны быть воспроизводимы.

    ● Минимум модели: 8–12 таблиц, 3+ внешних ключа, 1+ M:N связь, 1+ таблица с чувствительными данными.

    ● Безопасность по умолчанию: отключить public привилегии на новые объекты, использовать отдельные схемы (app, ref, audit, stg).

    ● Стиль SQL: явные списки столбцов; запрет SELECT * в prod-коде; комментировать объекты (COMMENT ON).

    ● Проверка: сценарии, показывающие успешные и запрещённые операции согласно политикам безопасности.

    ● Отчёт по каждой работе: цель, схема/диаграммы, принятые решения, скрипты, примеры запросов, результаты тестов, выводы.
